# 01. File storage in the database

**Goal:** Store uploaded files as `BYTEA` so the container needs no persistent volume.
**Depends on:** PostgreSQL support (done).
**Status:** draft for review — design agreed in discussion, not yet built.

## Why

PostgreSQL alone does not make the pod stateless. `services/FilesService.php` writes to
`GROCY_DATAPATH . '/storage'`, so product pictures, recipe pictures, user pictures, user
files and equipment manuals still need a volume.

The stronger argument than storage size: today `picture_file_name` lives in the database
and the bytes live on a volume — two independent backup streams that can disagree after a
crash. With `BYTEA`, hourly ZFS snapshots and nightly `pg_dump` capture metadata and bytes
atomically, and there is no PVC at all.

## What was measured before designing

| Finding | Consequence |
|---|---|
| PostgreSQL `BYTEA` reaches PHP as a **stream**; SQLite `BLOB` as a **string** | Backends must normalise. Moot given the PostgreSQL-only decision, but worth recording |
| `pg_column_size` == length for incompressible bytes | JPEGs do not TOAST-compress; storage ≈ actual bytes |
| `ImageResize::createFromString()` and `getImageAsString()` exist | Downscaling works on bytes — **no temp files anywhere** |
| Only three call sites outside `FilesService` | Small change, not a rewrite |

The real coupling is that the current code is **path oriented**: `file_exists`,
`mime_content_type($path)`, `fopen($path)`, `new ImageResize($path)`. That is what changes.

### Sizing, anchored on a real 30 MB database

```
originals   ~150 x 100 KB  = 15 MB      existing data  ~30 MB
recipes      ~50 x 200 KB  = 10 MB      => database    ~60 MB
thumbnails                 =  5 MB
```

A 60 MB nightly dump is seconds. Ten times wrong is still fine.

## Decisions taken

| Decision | Rationale |
|---|---|
| **PostgreSQL only** | Agreed. No SQLite BLOB backend; the config combination is rejected at startup |
| **Configurable**, `FILE_STORAGE = filesystem\|database`, default `filesystem` | Existing installs unchanged |
| **Thumbnails stored**, alongside originals | Cached on first request, as today, under the same `__downscaledto…` names |
| **No object store** | No MinIO/S3 path; churn after initial setup is near zero |
| **No `ETag`** | Response headers stay byte identical. Resizing is not a real workload on a CM5, which was its main justification. Trivial to add later |

## Proposed change

### Schema — migration `0256.pgsql.sql`, with no SQLite counterpart

The first deliberately engine-exclusive feature, which also exercises the per-engine
migration convention.

```sql
CREATE TABLE files (
  id            INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  file_group    TEXT NOT NULL,        -- not "group", reserved on both engines
  name          TEXT NOT NULL,
  mime_type     TEXT,
  size_bytes    INTEGER NOT NULL,
  is_derivative SMALLINT NOT NULL DEFAULT 0 CHECK(is_derivative IN (0,1)),
  content       BYTEA NOT NULL,
  row_created_timestamp TIMESTAMP DEFAULT date_trunc('second', LOCALTIMESTAMP),
  UNIQUE(file_group, name)
);
```

Derivatives are ordinary rows under today's exact naming, so the existing prefix-scan
delete logic becomes a `LIKE` and nothing else changes semantically. `is_derivative` means
every thumbnail can be dropped with one statement and regenerated — cheap insurance given
images are optional, and it keeps dumps trimmable.

### Code

New `Grocy\Services\Storage\FileStorage` with `FilesystemStorage` (today's behaviour,
unchanged) and `DatabaseStorage`:

```
Exists(group, name)          Read(group, name)  -> stream|null
Create(group, name, source)  -- exclusive, mirrors fopen('xb')
Write(group, name, source)   -- overwrite, mirrors file_put_contents
Delete(group, name)          ListNames(group, prefix)
GetMimeType(group, name)
```

Three call sites move: `FilesApiController` (serve/upload/delete), `FilesService`
(downscale/delete), and one line in `StockService:659` where barcode lookup writes a
product picture.

Config validation rejects `FILE_STORAGE=database` with `DB_DRIVER=sqlite` at startup,
with a clear message rather than a failure at first upload.

### API

No change. Same three routes, same headers, same 404 behaviour. `files` is deliberately
**not** added to `ExposedEntity`.

## Risks

- **`mime_content_type($path)` vs `finfo_buffer($bytes)` must agree**, or `Content-Type`
  shifts on an existing endpoint. Same magic database, so it should — verify against a real
  JPEG and PDF rather than assuming.
- **LessQL probably cannot bind LOBs.** Plan is raw PDO for the `content` column, verified.
- **PDO's `BYTEA` stream is tied to its statement.** Copy into `php://temp` (spills to disk
  past 2 MB) rather than handing Slim a lazily read handle that may outlive it.

## Open questions

1. **What happens to files already on disk when the setting is flipped?** The one open
   decision.
   - **(a) Explicit import.** `bin/grocy-files-import` walks `/data/storage` into the
     database; before it runs, images 404. One source of truth at any moment.
   - **(b) Read-through fallback.** Database first, filesystem for anything missing.
     Flipping Just Works, but a file can live in two places indefinitely.

   I lean to **(a)** — a lingering filesystem fallback is a trapdoor back to needing a PVC,
   which is the thing this removes.

   > **Response:** (a), and the k3s context strengthens it: run the import as a
   > one-off Job against the PVC before flipping the Deployment to the volume-less spec.
   > Make the importer idempotent (skip rows that already exist with identical size)
   > so a crashed Job can simply re-run. A read-through fallback means the PVC can
   > never be deleted with confidence.
2. **Size cap.** Proposing `FILE_STORAGE_MAX_SIZE_MB`, default 64. Not about OOM on 16 GB,
   but `userfiles` and `equipmentmanuals` accept arbitrary uploads and a bound you can raise
   beats an unbounded read.

   > **Response:** Yes — and validate it against PHP's own `upload_max_filesize` /
   > `post_max_size` at startup: a `FILE_STORAGE_MAX_SIZE_MB` larger than what PHP
   > accepts is a lie, and one smaller is the real bound. Report the effective
   > value.
3. **Reverse migration?** Proposing not to build one. `pg_dump` plus a script is a later
   problem if it ever comes up.

   > **Response:** Agreed, don't build it. `COPY (SELECT content ...) TO` plus a
   > shell loop covers the contingency.

## Review notes

- `Create` vs `Write` semantics: implement `Write` as `INSERT ... ON CONFLICT
  (file_group, name) DO UPDATE` so overwrite is atomic; `Create` as a plain insert
  letting the unique constraint signal "exists". Cheaper and more correct than
  exists-then-write.
- The `files` table will be the first engine-exclusive table. Check that
  `.devtools/pgsql/difftest.php` and `DatabaseImporter` tolerate a table that exists on
  one engine only, and note the exception in `db/pgsql/README.md` so the "every
  migration works on both engines" rule has its documented exemption.
- Thumbnails written on first request are a runtime DB write from a GET path. Harmless
  here, but worth a one-line comment in the code, since "GETs don't write" is otherwise
  a nice invariant.

## Effort

Small. Abstraction plus filesystem backend is a pure refactor that must leave behaviour
green; database backend and import command follow. One focused session.
